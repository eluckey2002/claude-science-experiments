# Audit — Agent Reasoning Failure Modes v2.2

Auditor: `FRESH_EYES_AUDITOR` sub-agent, no project context. Source document: `agent-failure-modes.json` (23 modes, 4 stages, 6 facets, telemetry schema, 20 references).

Fitness judged against three stated uses: **(a)** a rater assigns a mode code to a trace; **(b)** the `reframe` string is injected into a prompt; **(c)** detections are logged to the telemetry schema and counted by mode/stage across runs.

## Verdict

NOT READY for use (c) as written; usable for use (a) with a rater guide; usable for use (b) after the fix/reframe duplication is resolved. Ten blocking defects. The load-bearing one is discriminability inside the Verification stage: C2, C3 and C4 carry identical facet vectors and tells that a single trace can satisfy simultaneously, with C5 overlapping all three, so per-mode counts in F3 — a quarter of the taxonomy — are set by the rater rather than by the agent's behaviour. The trajectory cluster has the same problem: B5/D1 are separated by a single facet (direction), and D2/D3 by two (direction and intervention) while sharing locus, temporal, detectability and family. Second, the facet space is less informative than it presents: locus=process-inertia is exactly temporal=trajectory and locus=gate-lax is exactly stage F3, so slicing by locus re-reports partitions already available, and any locus-temporal correlation is 1.0 by construction. Answering the question posed directly — these are one axis named twice as instantiated; keep temporal, which is mechanically checkable, and drop or re-assign process-inertia. Third, the telemetry schema cannot support the analyses it claims: no taxonomy_version (codes demonstrably change — 8 modes carry added_in of v2 or v2.2), no denominator for 'failure rate over time', no rater_id or secondary-assignment field, so the discriminability problem is invisible in the resulting data. On citations, I checked eleven attributions against sources and found four defects: C5's MAST 'Premature Termination' is a different construct from the confident-completion behaviour C5 describes; A2 cites the GPT-3 paper for a failure mode it does not document (the support is Zhao 2021 / Min 2022); B7 attaches Knuth's premature optimization to premature abstraction, which it does not cover; and references[5] attributes Strathern's 1997 formulation to Goodhart 1975. D4 fuses a trace-visible MAST construct with Turpin's counterfactual-only one and tags the result trace-visible. Nine attributions I did not check are listed as unverified. Against this, three things are done unusually well and should be kept as the pattern for the rest: A5's citation explicitly refuses to invent a source; C6, A4 and A5 each contain an in-detail contrast sentence against their nearest neighbour, and they are the file's least confusable entries; and the reframes as a group are markedly more actionable than the tells — only D4, B1 and B8 are restatements. Coverage: ten concrete gaps, of which the two I would add first are fabricated verification (claiming a check with no corresponding trace action — trace-visible, and it corrupts every other count) and tool-output misread (empty result read as 'none exist', error read as success), which is probably the single most common reasoning failure in real agent traces and has no code.

## Declared limits of this audit

- Citations: 11 of 23 source attributions checked against primary sources (MAST arXiv:2503.13657 full text; Turpin arXiv:2305.04388 abstract; web searches for Knuth 1974, Goodhart/Strathern, the A2 in-context-learning literature). A3, B1, B2, B4, B5, B6, B8, C1, C4 and A5 were not fetched — assessed for bibliographic plausibility only and flagged `verified: false`; any 'no defect' call on them is provisional.
- The B3 anchoring finding rests on the standard definition of anchoring-and-adjustment, not a re-read of Tversky & Kahneman 1974.
- Discriminability was assessed analytically from tell/detail/facet text plus a computed facet-vector distance matrix. No rater experiment was run — the claim is that code assignment is under-determined by the document, not a measured disagreement rate.

## Blocking defects (10)

### 1. discriminability — `stages[2].failure_modes[1..4] (C2,C3,C4,C5)`

> C2.tell: "Glides to the end, never checks." | C3.tell: "Checks the surface only." | C4.tell: "Tests one case, assumes the rest." | C5.tell: "Looks done; isn't verified."

**Defect.** Four of the six Verification modes partition a single observable — 'the result was not adequately checked' — along distinctions that are not recoverable from a trace. C2/C3/C4 additionally carry IDENTICAL facet vectors (gate-lax, under-shoot, single-step, trace-visible, reframe-sufficient, closure), so the facets offer no tie-break either. A trace showing one quick passing test on the happy path followed by a confident summary satisfies all four tells simultaneously: no real check (C2), surface check (C3), single case (C4), polished done-signal (C5).

**Consequence in use.** Use (c) breaks: per-mode counts inside stage F3 are set by which rater or judge prompt is used, not by what the agent did. Two runs of the same harness with different judges are not comparable, and F3 is where the taxonomy puts a quarter of its modes.

**Fix.** Make the F3 codes mutually exclusive on a trace-observable decision procedure applied in order, e.g. (1) is there any verification act in the trace? no -> C2; (2) does the act execute the artifact under test? no -> C3; (3) does it cover >1 case? no -> C4; (4) all of the above present and the result still asserted as complete without evidence -> C5. State that procedure in the document and require the rater to record which branch fired.

### 2. discriminability — `stages[1].failure_modes[4] (B5) vs stages[3].failure_modes[0] (D1); stages[3].failure_modes[1] (D2) vs stages[3].failure_modes[2] (D3)`

> B5.tell: "Won't abandon a failing approach." | D1.tell: "Repeats a step with no progress." -- and -- D2.tell: "Goal erodes across a long run." | D3.tell: "Drops earlier or mid-context constraints."

**Defect.** B5 and D1 differ on exactly one facet (direction: over-shoot vs mis-aim) and their tells do not name a discriminator. A retry loop against a failing approach is literally both. D2 and D3 share locus, temporal, detectability and family (salience) and differ on two facets (direction, and intervention: reframe-sufficient vs needs-tool); the goal is itself a constraint stated earlier, so an agent that forgets the objective in a long run satisfies both tells.

**Consequence in use.** Use (c): the trajectory cluster (B5,D1,D2,D3) is the only place the taxonomy can measure long-horizon degradation, and its internal allocation is rater-dependent. Cross-run trend claims about 'spinning' vs 'sunk path' are not comparable.

**Fix.** Add an explicit discriminator to each tell in the pattern C6 already uses. Suggested: B5 = the plan is retained while the actions vary; D1 = the action is near-identical across steps. D2 = the ORIGINAL OBJECTIVE is displaced by a self-generated sub-goal; D3 = a stated CONSTRAINT is violated while the objective is still being pursued.

### 3. facets — `facet_vocabulary.locus vs facet_vocabulary.temporal and stages[*].id`

> facet_vocabulary.locus: {"description": "What pulls the agent off course.", "values": ["input-shaped", "prior-driven", "process-inertia", "gate-lax"]}

**Defect.** locus is not an independent axis as instantiated. Computed over all 23 modes: locus=process-inertia = {B5,D1,D2,D3} = temporal=trajectory exactly; locus=gate-lax = {C1,C2,C3,C4,C5,C6} = stage F3 (verification) exactly. Two of locus's four values are re-encodings of axes already present. Only input-shaped/prior-driven carry information locus alone supplies.

**Consequence in use.** Use (c): the document presents six facets as six slicing dimensions. Slicing counts by locus and then by temporal/stage reports the same partition twice, which reads as two independent confirmations of one pattern. Any correlation computed between locus and temporal is 1.0 by construction, not a finding.

**Fix.** Answering the question posed: as instantiated these are ONE axis named twice, and temporal is the one to keep -- 'appears only over multiple steps' is mechanically checkable from a trace (count the steps), whereas 'what pulls the agent off course' is an attribution. Either drop process-inertia from locus and assign those four modes a genuine puller (B5 prior-driven, D1/D2/D3 process-native if you want the value), or drop locus and derive it. Same for gate-lax, which is stage F3 restated.

### 4. schema / reframe injection — `stages[0].failure_modes[3].fix (and A5,B8,C6,D1,D2,D3,D4)`

> A4.fix: "Ask one clarifying question before guessing." alongside A4.reframe: "If a load-bearing requirement is ambiguous, ask one targeted question before proceeding — don't guess silently." and A4.mitigation: "When a load-bearing requirement is ambiguous, ask a single targeted question before proceeding rather than committing to a guess."

**Defect.** `fix` exists on exactly 8 of 23 modes (A4,A5,B8,C6,D1,D2,D3,D4 — precisely the modes with new:true) and is declared nowhere in the document: there is no mode-object schema, and the field is absent from the task-facing field list. It is a third prescriptive string duplicating `reframe` and `mitigation`, with no stated precedence or intended consumer.

**Consequence in use.** Use (b) breaks silently: a prompt builder keyed on `fix` emits nothing for 15 of 23 modes and will appear to work because the 8 modes it does cover are the recently added ones. A builder keyed on `reframe` ignores `fix` entirely, so two implementations of 'inject the reframe' inject different text for the same mode code, and the intervention-efficacy numbers in use (c) are not comparable between them.

**Fix.** Either populate `fix` for all 23 or delete it. Declare which single field is the injectable string; `reframe` is the one the telemetry schema already references (intervention.reframe_text), so make that normative and demote `fix` to a UI short label under a name that says so (e.g. `short_label`).

### 5. facets / reframe injection — `stages[1].failure_modes[7].facets.intervention (B8), stages[2].failure_modes[5].facets.intervention (C6), stages[3].failure_modes[2].facets.intervention (D3) vs telemetry.event_schema.intervention.type`

> facet_vocabulary.intervention: {"description": "What resolves it.", "values": ["reframe-sufficient", "needs-tool"]} -- and -- telemetry.event_schema.intervention.type: "preflight | reframe | none"

**Defect.** Three modes are labelled needs-tool, i.e. by the document's own definition of the facet ('What resolves it') a reframe does not resolve them. All three nonetheless ship a reframe, and the telemetry intervention.type enum has no value for a tool intervention. The taxonomy therefore asserts a treatment it cannot record and ships a treatment it says is insufficient.

**Consequence in use.** Use (b): a harness that injects reframes for all 23 modes is applying a treatment the taxonomy predicts will fail for B8/C6/D3, with no way to mark it as such. Use (c): 'Intervention efficacy — resolved-rate per reframe' will report a low resolved-rate for those three and the cause will be unrecoverable from the log, because the tool intervention that was (or was not) applied has no field.

**Fix.** Add "tool" (and "tool+reframe") to intervention.type, and state what the required tool is for each needs-tool mode (B8: grounded retrieval/citation check; C6: test-file diff guard; D3: constraint re-injection). If no tool is specified the facet is unactionable and should be dropped.

### 6. citation / discriminability — `stages[3].failure_modes[3].citation (D4)`

> "Turpin, M. et al. (2023). Language Models Don't Always Say What They Think: Unfaithful Explanations in CoT Prompting. NeurIPS. MAST: reasoning–action mismatch (Cemri et al. 2025)."

**Defect.** D4 fuses two different constructs. I read both sources. MAST FM-2.6 'Reasoning-action mismatch' is defined as 'Discrepancy between the logical reasoning process and the actual actions taken by the agent' — trace-observable by comparing narration to the executed call. Turpin et al. measure something else: that CoT explanations 'can systematically misrepresent the true reason for a model's prediction', demonstrated by adding biasing features to the input and observing that models fail to mention them. That is detectable only by a paired counterfactual run, never from one trace. D4.facets.detectability is "trace-visible", which is true of the MAST reading and false of the Turpin reading.

**Consequence in use.** Use (a): a rater who has read Turpin looks for unmentioned influences and codes almost nothing; a rater who has read MAST codes every narration/action divergence. Use (b): D4.reframe "Make your action match your stated reasoning" addresses only the MAST reading — under Turpin's finding the model cannot report the true cause, and the instruction can be satisfied by revising the narration to fit the action, which makes the failure less visible rather than fixing it.

**Fix.** Split, or scope D4 to the MAST construct and cite only MAST. If the Turpin phenomenon is wanted, it is a separate mode with detectability: needs-ground-truth and intervention: needs-tool (counterfactual probe), not a reframe.

### 7. telemetry — `telemetry.event_schema`

> "mode_code": "string — e.g. 'B4' (FK to a failure mode)"

**Defect.** No taxonomy_version field. The document is v2.2, carries `added_in` values of "v2" and "v2.2" on 8 modes, and the codes are positional within a stage (A5 was appended at v2.2), so the code space is demonstrably mutable across versions.

**Consequence in use.** Use (c) breaks for exactly the purpose stated — 'counted by mode/stage over many runs'. An event store spanning a taxonomy revision cannot tell whether zero A5 events before a date means the behaviour did not occur or the code did not exist, and a re-lettered or split mode silently merges with its predecessor.

**Fix.** Add a required `taxonomy_version` (and ideally a content hash of the mode list) to every event, and freeze code-to-mode bindings across versions: retire codes, never reuse or renumber them.

### 8. telemetry — `telemetry.analyses_enabled[0] and [3] vs telemetry.event_schema`

> "Frequency — count per mode, sliced by stage / task_type / model." ... "Trend — failure rate over time or across model versions."

**Defect.** The schema records detections only. There is no run-level or step-level record of exposure: no total runs, no total steps, no record of which modes a given detector was even looking for on that run. A rate requires a denominator that the event stream does not contain.

**Consequence in use.** Use (c): 'failure rate' is not computable from these events, and raw counts confound behaviour change with monitoring-coverage change — adding a detector or running longer sessions raises the count with no change in agent behaviour. Trend and cross-model comparisons drawn from this stream will be wrong in a direction that flatters whatever was monitored least.

**Fix.** Add a companion run record (run_id, total_steps, model, task_type, detector set active, completed/aborted) emitted once per run, and define rate as detections per run and per step against it.

### 9. telemetry — `telemetry.event_schema.mode_code / telemetry.event_schema.detector`

> "detector": {"method": "monitor | preflight | self-report | human", "confidence": "number 0..1", "signal": "string — the tell/text that matched"}

**Defect.** One mode_code per event, no field for a competing or secondary assignment, and no rater/annotator identifier. Combined with the confusable clusters above, every genuinely ambiguous trace is silently resolved to one code with no record that a choice was made. There is also no way to compute inter-rater agreement, which is the only empirical check on the discriminability problem — MAST itself validated its 14 modes with an inter-annotator kappa of 0.88 and this schema cannot produce that number.

**Consequence in use.** Use (c): the taxonomy's central weakness becomes invisible in its own data. Counts look clean and precise while being rater-dependent.

**Fix.** Add `rater_id` (or judge prompt hash) and an optional `alternatives: [mode_code]` list; log the same trace under >=2 raters on a held-out sample per model version and publish kappa alongside the counts.

### 10. citation — `stages[2].failure_modes[4].citation (C5)`

> "Cemri, M. et al. (2025). MAST — “Premature Termination”; plus the overconfidence/calibration literature. arXiv:2503.13657."

**Defect.** Checked against the MAST paper (arXiv:2503.13657, HTML v3). MAST defines premature termination as 'Ending a dialogue, interaction or task before all necessary information has been exchanged or objectives have been met'. C5's detail is a different construct: "Delivers a polished, confident 'finished' signal that performs done-ness — the well-formatted answer that's wrong but reads as complete." MAST's mode is about stopping early; C5's diagnostic content is presentation and confidence, which MAST does not measure. Consistent with the mismatch, C5 is tagged direction: over-shoot while MAST's construct is an under-shoot. The second half of the citation, 'the overconfidence/calibration literature', names no work and has no entry in the 20-item `references` list — it is the only citation in the file with no resolvable referent.

**Consequence in use.** Use (c): MAST is the interoperability anchor for 7 of the 23 modes. C5 counts will be read as comparable to MAST FM-3.1 counts and are not. Use (a): a rater who consults the cited source is told to look for early stopping and will code the trace C5 for the wrong reason.

**Fix.** Cite MAST FM-3.1 only if C5 is re-scoped to early termination; otherwise drop it and cite the calibration work actually meant (and add it to `references`). Note MAST FM-3.2 'No or incomplete verification' is already correctly used by C2, so the early-stopping content may belong there.

## Reframes that restate the failure (7)

| Code | Text | Problem |
|---|---|---|
| D4 | Make your action match your stated reasoning. If they diverge, reconcile them before proceeding. | Restates the tell ("Reasoning says one thing; the action does another.") as an imperative and supplies no procedure. Worse, it is satisfiable in the wrong direction: revising the narration to fit the action 'reconciles' them and removes the evidence. Under the Turpin construct the mode also cites, the instruction is inert — the finding there is that the model does not report the true cause of its behaviour, so asking it to align the two cannot surface it. |
| B1 | Ask what data you'd need but don't have. Don't treat what's in front of you as the whole picture. | Second sentence is the tell ("Treats available data as the whole picture.") negated. The first sentence is the only operative content; the second adds length to an injected prompt without adding an instruction. |
| B8 | If you don't have a specific fact (citation, API, number), say so. Never invent specifics to complete the pattern. | Second sentence is the tell ("Invents specifics to complete the pattern.") negated. It also asks the model to apply a distinction — grounded vs generated — that it does not reliably have access to, which is exactly why the mode is tagged intervention: needs-tool. The reframe and the facet disagree about whether prompting is the treatment. |
| A3 | Re-anchor to the source facts. If this answer would change had the conversation been framed differently, you're echoing, not reasoning. | The second sentence asks for a counterfactual the model cannot run on itself in-context; it is a diagnostic criterion addressed to an analyst, mis-packaged as an instruction to the agent. 'Re-anchor' is also undirected — to which facts, retrieved how. |
| A1 | State the outcome the user actually wants — independent of how they phrased it — before acting on the literal words. | Presupposes access to the very thing the mode says is missed. It is an instruction to succeed, not a procedure: nothing tells the agent what to do when the phrasing is the only evidence of intent — which is the case that produces the failure. Compare A4's reframe, which gives a concrete move (ask one question). |
| B6 | Weigh by evidence, not balance. If the evidence is lopsided, let the conclusion be lopsided. | Actionable in direction but supplies no weighing procedure, and 'lopsided' is assessed against the same judgement that produced the failure. Borderline rather than a pure restatement. |
| A1 + A4 (interaction) | A1: "State the outcome the user actually wants — independent of how they phrased it — before acting on the literal words." | A4: "If a load-bearing requirement is ambiguous, ask one targeted question before proceeding — don't guess silently." | These two prescribe opposite actions on the same input. Under ambiguity A1 says infer the intent and act; A4 says do not infer, ask. A1.pairs_with lists A4 and A4.pairs_with lists A1, so any UI or harness following the cross-links will co-inject them. A4/A5 have the same relation (ask vs do not ask) and are also mutually cross-linked. The document gives no injection policy — how many reframes, chosen how, in what precedence — which use (b) requires and which also determines what 'intervention applied' means in the telemetry. |

## Facet findings (9)

- CO-EXTENSIVE AXES (the question asked): computed over all 23 modes, locus=process-inertia = {B5,D1,D2,D3} and temporal=trajectory = {B5,D1,D2,D3} — identical. Verdict: one axis named twice as instantiated. They are not conceptually identical (a gate-lax failure could in principle be trajectory-scoped, e.g. verification quality decaying over a long run), but no mode in this file exercises that combination, so in the data they will produce they are redundant. Keep temporal (mechanically checkable: does the failure require >1 step to appear) and drop or re-assign process-inertia. Full locus/temporal cross-tab: input-shaped x single-step = 5, prior-driven x single-step = 8, gate-lax x single-step = 6, process-inertia x trajectory = 4, all other cells empty.
- SECOND CO-EXTENSIVE PAIR, not flagged in the brief: locus=gate-lax = {C1,C2,C3,C4,C5,C6} = exactly the members of stage F3 (verification). So locus has two redundant values out of four, and only input-shaped/prior-driven carry independent information.
- A1 direction contradicts A4's own text. A4.detail (stages[0].failure_modes[3].detail): 'The complement of Literalism: under-asking rather than over-obeying.' The contrast asserts A1 over-shoots where A4 under-shoots. But A1.facets.direction = "under-shoot" and A4.facets.direction = "under-shoot" — the same value. Compare A5, whose parallel sentence ('The inverse of No Questions Asked — over-asking rather than under-asking') IS honoured by its facets (A5 over-shoot vs A4 under-shoot). Either A1 should be over-shoot or A4.detail's contrast is wrong.
- A5 family contradicts its stated relationship to A4. A5.detail calls it 'The inverse of No Questions Asked', yet A4.facets.family = "closure" and A5.facets.family = "input-conformity". Two modes that are inverses of each other on the same behavioural dimension should share a family and differ on direction, which is exactly the pattern their `direction` values already follow.
- C5 detectability contradicts its own tell. C5.facets.detectability = "needs-ground-truth", but C5.tell is "Looks done; isn't verified." — the second clause is an absence of verification, which is trace-visible and is precisely what C2 is tagged trace-visible for. Only the 'wrong' part of C5 needs an oracle. As written, C5 will be under-reported by trace-only critics that honour the facet.
- Three identical facet vectors, i.e. the facets cannot separate these modes at all: {A2,A3} (input-shaped, mis-aim, single-step, needs-ground-truth, reframe-sufficient, input-conformity); {B6,B7} (prior-driven, over-shoot, single-step, needs-ground-truth, reframe-sufficient, closure); {C2,C3,C4} (gate-lax, under-shoot, single-step, trace-visible, reframe-sufficient, closure). A further 18 pairs differ on exactly one facet. For a 23-item taxonomy with a 6-dimensional facet space, the facets are carrying much less discriminative load than their presence implies.
- Facet-value balance is poor enough to make some slices uninformative: intervention is 20 reframe-sufficient / 3 needs-tool; temporal is 19 / 4; family=closure holds 9 of 23 modes (A4,B6,B7,C1,C2,C3,C4,C5,C6) and subsumes all of F3 plus three others. A 'family' slice is close to a 'was it verification' slice.
- Stage F4's question ('Did it hold the thread across steps?') vs D4.facets.temporal = "single-step": D4 is the only member of the trajectory stage that the facets say is not a trajectory phenomenon. Either D4 is misplaced in F4 or its temporal value is wrong; a rater partitioning by 'is this a multi-step failure' will not look in F4 for it.
- No mode uses the combinations (input-shaped, trajectory) or (gate-lax, trajectory). If those are impossible the vocabulary should say so; if they are possible they are coverage gaps — a constraint dropped because a tool result reshaped the task (input-shaped x trajectory) and verification quality decaying over a long run (gate-lax x trajectory) are both real.

## Telemetry findings (12)

- BLOCKING (listed above): no taxonomy_version; no denominator for the rate and trend analyses claimed in analyses_enabled; one mode_code per event with no alternatives list and no rater_id, so inter-rater agreement — the only empirical test of the discriminability problem — is uncomputable.
- mode_code and stage are both stored although stage is functionally determined by mode_code ('mode_code': 'string — e.g. B4 (FK to a failure mode)', 'stage': 'string — framing | reasoning | verification | execution'). Nothing constrains them to agree, so the store can hold rows where B4 is tagged stage 'framing'; a stage-sliced count then disagrees with a mode-sliced count rolled up to stage. Derive stage at query time, or add the constraint.
- 'preflight' appears with two different meanings and is defined nowhere: detector.method: 'monitor | preflight | self-report | human' (a detection channel) and intervention.type: 'preflight | reframe | none' (an injection timing). A field whose values are undefined will be filled inconsistently across harnesses, which is the failure mode the schema exists to prevent.
- detector.signal: 'string — the tell/text that matched' is unfillable as specified for most modes. It presumes the tells are matchable strings; they are compressed diagnoses (see weak_tells). In practice the field will hold a rater's free-text paraphrase, so it cannot be used to audit detector precision or to compare detectors — which is what a 'signal' field is for.
- outcome.resolved: 'boolean | null' cannot be determined from the trace for the 11 needs-ground-truth modes (A1,A2,A3,B1,B2,B3,B6,B7,B8,C1,C5), and no field records HOW resolution was adjudicated. 'Intervention efficacy — resolved-rate per reframe' will therefore mix oracle judgements with the agent's own self-report and will be systematically higher for trace-visible modes. Add an `outcome.adjudicated_by` with the same enum as detector.method, and treat resolved-rates as non-comparable across detectability classes.
- intervention.applied: 'boolean' and intervention.type: '... | none' encode the same information and can contradict each other (applied: true, type: none). Drop `applied` and treat type: none as not-applied.
- intervention.type has no value for the tool interventions that three modes require by their own intervention facet (B8, C6, D3). See blocking.
- No field identifies the taxonomy entry's prescriptive text version beyond the inline reframe_text. Storing the text inline is the right call and does let you group an A/B by exact string — but only if harnesses inject `reframe` and not `fix`; with two undocumented candidate strings per mode for 8 modes, grouping by text will split one experiment into two arms that look like two treatments.
- severity ('low | med | high | critical') sits in context_tags alongside model and domain. Severity is a per-detection judgement, not a property of the run context; putting it in a free-form tags object means it will be missing on some events, and 'Hotspots — stage/tag combinations with the highest failure density' depends on it being present. Promote it to a top-level field with a stated rubric.
- Co-occurrence analysis is supported only implicitly, via two events sharing run_id and step_index. That works, but chaining.note says pairs_with should be refined against real co-occurrence, and pairs_with is directional ('lists modes it tends to trigger or mask') while same-step co-occurrence is symmetric. To test a directional hypothesis you need the triggering event identified; add an optional `caused_by_event_id`.
- No field records the trace or run artifact the excerpt came from (a path, a URI, a content hash). trace_excerpt alone is not re-auditable — a disputed assignment cannot be re-examined in context, which matters most for exactly the confusable clusters above.
- example_event is internally consistent (mode_code B4 with stage 'reasoning' matches the file, and reframe_text is byte-identical to B4.reframe). Verified; no defect.

## Improvements (8)

- Add a mode-object schema (JSON Schema or an explicit field table) to the document. The audit found `fix` on 8 of 23 modes and `added_in` on the same 8, both undeclared; a schema plus a validator run in CI would have caught that and would catch code/stage drift in future versions.
- Adopt C6's disambiguation pattern as a requirement: every mode whose pairs_with is non-empty carries one sentence in its detail contrasting it with each linked mode. C6 does this ('Distinct from Closure Performance, which only looks done — this forces the gate.'), A4 and A5 do it for each other, and those are the three least confusable entries in the file. Eleven modes have empty pairs_with and no contrast sentence at all.
- Reconsider metaphor labels for use (a). 'Sailing' (C2), 'Skating' (C3), 'Spinning' (D1) and 'Drift' (D2) carry no diagnostic content for a rater or a judge model reading the label alone, and Sailing/Skating are near-homophones for adjacent codes — a transcription or judge-output error between C2 and C3 is both easy to make and invisible in the counts. Labels like 'No Verification' / 'Shallow Verification' would cost nothing in use and remove a class of silent miscoding.
- Add an `observable` field distinct from `tell`: what a reader would literally see in the trace, written in the agent's vocabulary rather than the analyst's. `tell` then stays as the human mnemonic and `detector.signal` gets something it can actually reference.
- State an injection policy for use (b): how many reframes are injected, selected by what (stage, prior failure history, task type), and what happens when two selected reframes conflict (A1/A4 and A4/A5 are direct conflicts and are cross-linked to each other). Without it, 'intervention applied' is not a defined treatment and efficacy numbers are not comparable between harnesses.
- The pipeline framing implies F1->F2->F3->F4 ordering ('pipeline_order'), but the F4 modes are cross-cutting: they can occur during framing, reasoning or verification within a long run. Verification is also not a phase that follows execution — it happens inside it. Consider presenting F4 as a scope dimension rather than a fourth stage, or say explicitly that stage is a category of failure and not a position in time; otherwise stage-sliced counts will be read as a temporal profile of the run.
- `new: true` and `added_in` overlap; `new` is a flag that will be wrong at the next version bump and will need a sweep across 23 entries. `added_in` alone carries the information — derive `new` at render time by comparing against the document version.
- Consider recording, per mode, the minimum evidence a rater must cite to assign it (e.g. C4 requires a pointer to the single test; D1 requires two step indices). This is the cheapest available lever on rater-dependence and it makes assignments auditable after the fact.
