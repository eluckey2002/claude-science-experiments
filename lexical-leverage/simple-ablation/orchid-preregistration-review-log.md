## Main findings

**M1 — SUPPORTED can be reached when "simple" has no effect, and FALSIFIED is nearly unreachable.**
The question is whether the word "simple" *causes* divergence. The causal contrast for that is vague vs. absent (A − B). But the only interval test in P1 is on A − C, and the A ≥ B condition is a point-estimate inequality that holds trivially at A = B. So the following data pattern is classified SUPPORTED: A = B exactly (the word does nothing), C well below both (the constraints in arm C reduce variability, as constraints do). The consuming decision then commits to a paraphrase-controlled confirmation of an effect that was never shown.
On the other side, FALSIFIED requires the *reverse* ordering with an interval excluding 0. The informative null — A − B tightly centred on zero — is classified INCONCLUSIVE forever, no matter how much data accumulates. A registration that cannot be falsified by a precise null is not falsifiable.
Fix: (a) make A − B the primary contrast with its own task-level CI; keep A − C as the secondary contrast ("does the same intent, stated concretely, remove the divergence"). (b) Name a smallest effect size of interest, δ, now — e.g. 0.05 (one fuzz slot in twenty) or a fraction of the calibration arm's effect — and define FALSIFIED as "the CI on A − B lies entirely inside ±δ". INCONCLUSIVE is then what remains: a CI that straddles both 0 and δ. That is the only way the INCONCLUSIVE branch's "add n vs. fix instrument" decision has a target to aim at.

**M2 — Arm C's constraints don't touch what the fuzzer measures.**
The instrument reads behavioural divergence on inputs — what a function does on an empty list, a negative int, an empty string. Arm C's constraints (stdlib only, at most one helper, no `__main__`) are structural: they say nothing about behaviour on any input. A model can obey all three and still make any edge-case decision it likes. So B > C, which P1 requires for SUPPORTED, will either fail for a reason unrelated to the hypothesis (C ≈ B because the constraints are orthogonal to the instrument) or pass only because fewer moving parts mechanically lower variance — which is not a finding about "simple" either. Task01's operationalized arm addressed the parser's actual behaviour; this one doesn't have that property.
Fix options: (a) redefine C so the concrete reading of "simple" lands on the measured dimension — e.g. `"Constraints: handle exactly the inputs the docstring describes; for anything else raise ValueError. Standard library only."` — which is still task-agnostic and is a defensible reading of "don't over-engineer"; or (b) keep C as written but drop B > C from the SUPPORTED condition and demote C to a descriptive secondary, stating plainly that it tests "does adding structural constraints reduce divergence", not "does operationalizing simple reduce divergence". Either is fine; the current text does neither.

**M3 — The fuzz-input mix decides what "disagreement" means, and it isn't pre-registered.**
On in-domain inputs, two correct implementations agree by definition — divergence there is *bugs*. On out-of-domain or edge inputs the spec is silent, and divergence there is the *silent-decision* phenomenon the study is about. The registration's typing rule mentions "task-appropriate range" for ints and includes empty strings/lists, but never fixes the proportion of edge vs. in-domain probes, and "task-appropriate" is a per-task judgment left to whoever codes the fuzzer — undisclosed flexibility in the instrument. With 20 random draws per task, the chance that a specific edge case (empty input, zero, negative, singleton) is even present varies task to task, which adds instrument noise on top of model noise.
Fix, three parts: (a) split the 20 slots into a fixed number of deterministic edge probes (empty, singleton, zero/negative or boundary value, one oversized input — say 5–6 slots) and the remainder random in-domain; (b) run each task's canonical `solution` field on the 20 probes to get a reference fingerprint — this is free, and it replaces the 30 hand-written implementations that control C1 currently demands (which is exactly the per-task manual cost the benchmark move was meant to avoid); (c) pre-register a decomposition of disagreement into slots where the canonical solution returns cleanly (divergence = bugs, or the canonical solution's own silent choice) and slots where it raises (divergence = genuinely unspecified behaviour). The hypothesis predicts the "simple" effect should live in the second bucket; if it lives in the first, that is a correctness story, not an ambiguity story, and P2's coarse parity check would not catch it.

**M4 — Temperature is the mechanism, not a nuisance parameter.**
Run-to-run divergence exists only because sampling is stochastic. "Fixed default, snapshotted into the run log" is fine for reproducibility but not for design: the floor/ceiling rule tells the experimenter to *lower* the temperature on a ceiling result, which can't be reasoned about without knowing the starting value, and if the default is low (or 0 with a near-deterministic endpoint) five reps can be identical for every arm and the whole run is a floor by construction. Resolve `host.llm`'s effective default now, write the number into the registration, and state why it is the right value for measuring variability.

## Minor findings

- **Renaming leaves the original name in the docstring.** HumanEval prompts carry doctest examples (`>>> below_zero([1, 2, -4, 5])`). Renaming only the `def` line leaves the retrieval cue in place and introduces an inconsistency (function is `solve`, examples call `below_zero`) that a model may "repair" by renaming back — which then breaks the harness call. Rename consistently throughout the prompt, apply the same rename to `Vagueness_prompt` for arm D, and add a post-extraction check that a callable with the registered name exists; if not, count it as an extraction failure rather than letting it surface as 20 identical `NameError` slots (which would read as *agreement*).
- **The 0.85 similarity threshold conflates memorization with "one obvious way to write it".** Many HumanEval solutions are 2–4 lines; two independent correct implementations of `below_zero` will score high on `SequenceMatcher` regardless of memorization. Calibrate: compute similarity between the canonical `solution` and the independently written C2 implementations, and set the memorization bar relative to that baseline rather than at an absolute 0.85.
- **Slot-equality rules are unspecified.** How are two exceptions compared (type only, or type + message)? What float tolerance applies for `float` / `List[float]` returns (summation order alone can differ in the last bit)? Is there a per-call timeout for fuzzed inputs that cause non-termination, and how is a timeout recorded? Do two all-slots-error reps count as agreeing (identical fingerprints) or as maximally divergent from each other? Each of these is a place the analysis could flex after seeing data.
- **Extraction failure rate is a per-arm confound.** If one arm produces more non-compliant responses (e.g. prose around the code, two fenced blocks), its disagreement rises for reasons of format compliance, not silent decisions. Report extraction-failure rate per arm and pre-register the primary analysis both with and without extraction failures.
- **The permutation test's statistic isn't named.** "Shuffle the four arm labels and recompute the aggregate" describes an omnibus test of "any arm differs". State the statistic it corroborates — the mean over tasks of the per-task A − B difference (and separately A − C) — so it matches the contrast it is meant to back.
- **P2's "1/5" has no unit.** "Mean task-pass-rate per arm" could be the fraction of reps passing averaged over tasks, or the fraction of tasks with all five reps passing. Define it; 0.2 means very different things under the two readings.
- **Arm D's disagreement includes correctness loss.** `Vagueness_prompt` deletes functional detail, so many D completions will fail the oracle; their divergence is partly "wrong in different ways", not "silent choice among valid options". Report D's pass rate next to the A / D ratio so the calibration isn't read as like-for-like.
- **Spend is all-or-nothing.** The floor/ceiling rule fires only after all 600 calls. A pre-registered go/no-go gate — arm B only, 5 tasks × 5 reps (25 calls, ~4% of the budget) — checking that baseline disagreement is above floor would catch the most likely failure mode before the remaining 575 calls. It doesn't bias the arm contrast because it looks at one arm only; the 25 completions can be kept as part of the main run.
- **C2's edge cases are chosen by someone who knows the fuzzer.** Pre-specify the edge-case categories the five positive-control pairs must span (empty input, singleton, boundary value, type edge such as whitespace-only string) so the control can't be tuned to what the fuzzer is already good at. With the deterministic edge probes from M3 this becomes straightforward.
- **Call order.** State that the 600 calls are interleaved across arms and tasks (not run arm-by-arm), so any endpoint drift during the run is spread across arms rather than confounded with one.
- **Only one standby task.** If two sampled tasks fail the run-time check there is no rule. Say "extend k in the seeded sample as needed, taking standbys in order".
- **"Each run reports success" is in the question but not in the measurement.** The oracle pass stands in for it. Say so in Scope, so the result isn't read as evidence about the model's self-report.
