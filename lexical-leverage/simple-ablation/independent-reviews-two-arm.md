# Independent reviews — two-arm pre-registration v1 (Reviewers C, D)

**Reviews:** `simple-ablation-two-arm-preregistration.md` v1, artifact `4d989218-f6e2-41a4-99f0-d5e7ddbb9057`, version `af9b0352-997e-45af-95f9-2eaf2511f64d`.
**Method:** two fresh-context reviewers; saw only the v1 document and house conventions. Both declared full coverage. Both: not fundable as written.
**Disposition:** all main findings and most minor ones applied in v2 of the registration (same artifact, new version). Delta review of v2 follows separately.

## Reviewer C (frame `0d206370-e8aa-4539-b2fc-e6003ca19827`) — fundable as written: False

**Verdict.** This two-arm reduction genuinely fixes the three structural defects the prior independent reviews found in the four-arm design: the primary contrast is now A-B (matching the stated research question) rather than A-C; FALSIFIED is now a real symmetric equivalence-style test on the CI (interval inside [-delta,+delta]) that a genuine null can actually satisfy, rather than a point inequality that only a reversal could fail; and the manipulation (a natural-language suffix) is on the same behavioral dimension the fuzzer reads, whereas the old operationalized arm read structure. Slot-equality and fuzz-generation rules are now concretely specified rather than left as prose. However, three problems remain that a careful reviewer would not wave through: there is no power/precision justification for spending 300 model calls on a design whose own text predicts INCONCLUSIVE as the modal outcome; the 'frozen' probe set is generated from Python's built-in hash() of the task name, which is not deterministic across process runs by default, so the specification as written cannot actually be re-derived or audited; and the specified/unspecified slot split silently conflates behavioral ambiguity with 2-second timeout artifacts on computationally heavy probes (int 10**6, length-200 lists/strings), which can mislabel a complexity artifact as 'unspecified behavior' and contaminate exactly the secondary analysis (unspecified-slot Delta) that is supposed to isolate the ambiguity story from the correctness story -- and the one control aimed at reference-implementation soundness (C1, determinism) cannot catch this, because a reference that reliably times out produces an identical fingerprint on both runs and passes C1 regardless.

### Main findings

**1. No power/precision justification for n=30 tasks x 5 reps against delta=0.05**

*Problem.* The registration picks delta = 0.05 ('one probe slot in twenty') as the smallest effect of interest and a 90% task-bootstrap interval, but never shows that this sample size can actually resolve the SUPPORTED/FALSIFIED boundary. The document states outright: 'At 30 tasks INCONCLUSIVE is the expected modal outcome; that is acceptable because it now has a real boundary with FALSIFIED.' Having a real boundary is necessary but not sufficient -- a boundary the study is unlikely to ever land on either side of doesn't make the spend informative.

*Why it matters.* 300 model calls are being committed to a design that, by its own admission, will most likely return 'come back with more tasks' rather than an answer. Without a power calculation (analytic or a quick Monte Carlo using a plausible variance estimate for per-task disagreement), there's no way for a funder to judge whether the chosen n is close to sufficient (in which case doubling it might resolve the question) or wildly insufficient (in which case this run is a pure pilot and should be scoped and funded as one).

*Fix.* Before running, simulate the bootstrap+permutation decision rule under a few plausible true-Delta values (e.g. 0, 0.03, 0.05, 0.08) using a rough estimate of per-task variance (from the C6 gate data or a small pilot), and report the resulting SUPPORTED/FALSIFIED/INCONCLUSIVE probabilities. If power to detect delta=0.05 is low, either raise delta to a value the sample can actually resolve, or explicitly register this run as a pilot whose primary deliverable is a variance estimate for a properly powered follow-up.

**2. Frozen probe generation depends on non-deterministic hash()**

*Problem.* Slots 7-20 are generated 'with random.Random(hash of task name)'. Python's built-in hash() for strings is salted per-process by default (hash randomization / PYTHONHASHSEED) unless explicitly disabled, so this seed -- and therefore the entire 20-probe set for every task -- is not reproducible from the written specification alone; two runs of the generation code in different processes can legitimately produce different probes.

*Why it matters.* The document's central integrity claim is that probes are 'frozen before any model call and never shown to the model.' A specification that can silently drift between the moment it is written and the moment the generation script actually runs (or between the registration author's environment and an auditor's) is not actually frozen -- it only looks frozen. This is the same class of problem ('fuzz ranges are not actually frozen') the prior independent reviews already flagged against the four-arm version; pinning the numeric ranges without pinning the seed derivation only half-fixes it.

*Fix.* Either pin PYTHONHASHSEED=0 for the generation run and state that explicitly as part of the frozen procedure, or (better) replace hash(task_name) with a deterministic hash (hashlib.sha256(task_name.encode()).hexdigest() cast to int). Then archive the actual generated 20-probe-per-task set (or its checksum) as a companion artifact at registration time, so the frozen inputs are verifiable data, not just a formula.

**3. Specified/unspecified slot split conflates ambiguity with timeout artifacts, and C1 cannot catch it**

*Problem.* A slot is labeled 'unspecified' whenever the canonical solution raises or times out on it. But several deterministic edge probes are explicitly oversized ('a string of 200 chars, list of 200 elements, int 10**6') and every call runs under a flat 2-second timeout. If a correct-but-unoptimized canonical solution simply needs more than 2 seconds on one of these inputs, that slot gets classified 'unspecified' for a reason that has nothing to do with the prompt leaving behavior unspecified -- it is a runtime-budget artifact. C1 ('run the canonical solution against its 20 probes twice; fingerprints identical') is described as the safeguard against reference-implementation problems, but a solution that reliably times out produces the identical ProbeTimeout fingerprint on both runs and passes C1 cleanly.

*Why it matters.* Secondary analysis 1 -- the one analysis specifically designed to test 'the hypothesis predicts the effect lives in the unspecified slots' -- is exactly the analysis this contaminates. If timeout-driven pseudo-unspecified slots are unevenly distributed across the 30 tasks (likely, since task computational profiles differ), the specified/unspecified split stops cleanly separating 'ambiguity story' from 'correctness story' as claimed, and no control in the registration is positioned to detect this -- it is a case of a control passing while the underlying instrument problem remains live.

*Fix.* Before freezing, run the canonical solution against all 30 x 20 probes once and check elapsed time per slot; any slot where the canonical solution needs a non-trivial fraction of the 2-second budget (or times out) should be flagged and either given a longer timeout for that specific probe or dropped/regenerated. Add this as its own control (e.g. C7: canonical-solution timeout audit) run before any of the 300 model calls, distinct from C1.

### Minor findings

- **Extraction-failure fingerprints can bias the primary metric, only partly guarded.** Two extraction failures are defined to fully agree with each other (all 20 slots ExtractionFailure), so an arm with a higher extraction-failure rate gets its within-arm disagreement pulled toward 0 by construction, independent of how divergent the executed completions actually are. Secondary analysis 2 (excluding extraction failures) is a real safeguard -- if it disagrees with the primary in sign or classification the run is reported INCONCLUSIVE -- but the primary decision itself is still computed on the unadjusted metric first. Recommend also reporting a formal test on the per-arm extraction-failure rate difference itself, since that rate is informative about formatting effects of the 'Keep it simple.' suffix independent of behavioral divergence.
- **Any-appended-text vs. the word 'simple' confound is disclosed but still costs the full budget.** Arm A differs from arm B only in the presence of an appended clause, so even a clean SUPPORTED result cannot distinguish 'the word simple changed something' from 'any trailing sentence changed something' (length, an extra paragraph break, an extra imperative sentence of any content). The registration is honest about this in Scope ('Cannot claim: that the effect is due to the word rather than any appended text') and correctly defers the paraphrase control to a follow-up rather than overclaiming -- this is good practice, not a hidden flaw. But it does mean the entire 300-call run, even in the best case, only motivates a second registration rather than answering the motivating question about 'simple' specifically. Worth considering whether a length/paraphrase-matched third arm could be folded into this run cheaply rather than requiring a full second task-bank/fuzzer setup later.
- **Memorization-diagnostic calibration bar is a 90th percentile of only 10 samples.** C2 provides exactly 10 hand-written-implementation-vs-canonical ratios (5 tasks x 2 implementations), which is the minimum needed to avoid the 0.85 default -- but a 90th percentile estimated from n=10 is essentially just the second-highest of 10 draws, extremely sensitive to which two implementations were hand-written. This only affects the INCONCLUSIVE-branch diagnosis, not the primary SUPPORTED/FALSIFIED test, so it is not fund-blocking, but the bar should be treated as provisional/noisy in any report that relies on it.
- **C6 baseline-gate threshold's illustrative arithmetic is loosely stated.** The parenthetical gloss on the 0.02 threshold ('at least one disagreeing slot in fifty pair-slots') is only exactly right for a single task's 200 slot-observations (10 pairs x 20 slots); as stated it is applied to a mean across 5 tasks, where the equivalence is looser. Not wrong, but worth restating precisely so a reader can verify the number without reconstructing the arithmetic themselves.
- **Permutation test does not state that the 5/5 A-B split is preserved under label shuffling.** 'Shuffle the A/B labels among its 10 completions' should explicitly state whether the shuffle preserves the 5-and-5 group sizes (standard for this kind of permutation test) or allows arbitrary splits -- the two give different null distributions.
- **No minimum-unspecified-slot-count safeguard for secondary analysis 1.** Tasks with zero or very few 'unspecified' slots (by the raises/times-out definition) contribute little or nothing to the unspecified-slot restricted analysis; since this is explicitly descriptive rather than a decision-triggering test, this is a precision footnote rather than a validity problem, but should be reported (e.g. the distribution of unspecified-slot counts per task) alongside that analysis.

### Done well

- Primary contrast is Delta = disagreement(A) - disagreement(B), directly matching the stated research question -- fixes the prior four-arm version's A-vs-C mismatch.
- FALSIFIED is a genuine symmetric equivalence-style test (CI entirely inside [-delta, +delta]) that a true null can actually satisfy, rather than a point inequality only a reversal could fail.
- Slot-equality rules are concretely pinned (math.isclose tolerances, exception-type-only matching, timeout as its own type) and fuzz-generation ranges are spelled out per parameter type -- resolves the prior 'not actually frozen' critique on both fronts (except for the hash() seeding issue noted above).
- The manipulation (a natural-language suffix) and the instrument (behavioral fuzzing) now read the same dimension, fixing the structural-vs-behavioral mismatch that made the old operationalized arm uninformative.
- Bootstrap resamples at the task level (not the completion level), correctly treating task as the unit of independence given within-task correlation across reps.
- All 300 (task, arm, rep) calls are interleaved in one shuffled call order with logged timestamps, avoiding temporal/order confounds between arms.
- C6 is a genuine sequential stop rule that risks only 25 of 300 calls to verify the instrument has any sensitivity before committing the rest of the budget.
- C2/C3 require the fuzzer to actually separate deliberately-differing hand-written implementations before trusting it on real model output -- a real positive control, not just a sanity check.
- Scope section is explicit and appropriately conservative about what a result can and cannot support, including naming the appended-text confound rather than hiding it.
- Consuming decision is named for all three outcomes (SUPPORTED, FALSIFIED, INCONCLUSIVE), including sub-branches (memorization, floor, ceiling) for INCONCLUSIVE.

## Reviewer D (frame `16cf8bba-f0d2-49c0-bcc7-f2f022737e50`) — fundable as written: False

**Verdict.** This is a substantially more disciplined document than a typical pre-registration, and most of the core measurement machinery (paired task design, frozen fuzz probes with a real positive control, execution-only oracle, permutation test on the correct unit) is sound. But it is not internally executable as written: the Design section's frozen call order ('all 300 triples shuffled ... run in that interleaved order') directly contradicts control C6, which requires 25 of those same 300 calls (arm B only, on 5 named tasks) to run first as a stop-gate. That is not a stylistic nit — it means the protocol does not actually specify what happens at run time, which is exactly the kind of frozen-but-actually-ambiguous rule the pre-registration format exists to prevent. Layered on top of that: a stale cross-reference (the specified/unspecified split is said to 'replace hand-written reference implementations in control C1', but C1 as defined here is a pure determinism check with no hand-written implementations — that description matches C2) suggests the four-arm-to-two-arm edit was not checked end to end. And the secondary-analysis machinery meant to carry the paper's central mechanistic claim (is the effect an 'ambiguity story' or a 'correctness story') rests on a single canonical solution's arbitrary error-handling choices, not on the specification itself. None of these are fatal to the underlying idea, and all are fixable in an afternoon, but as written the run should not be funded.

### Main findings

**1. Call-order rule contradicts control C6 — the protocol does not specify what actually happens at run time**

*Problem.* Design states the frozen call order is: 'all 300 (task, arm, rep) triples shuffled with random.Random(20260926) ... and run in that interleaved order, timestamps logged.' Control C6 then requires 'arm B only, 5 tasks (the C2 tasks), 5 reps = 25 calls' to run as a gate 'before any of the 300 model calls' (per the Controls section header), and explicitly says 'these 25 completions are kept and count toward the main run' — i.e. they are part of the 300, not extra. Both rules cannot hold simultaneously: either the 300 are a single shuffled interleaving (in which case C6 cannot run to completion 'before' the other 275, since its 25 calls are scattered through the shuffle by construction), or the C6 subset runs first as a block (in which case the call order is not the single frozen shuffle the Design section describes).

*Why it matters.* This is not cosmetic: if C6's 25 arm-B calls for those 5 tasks are actually executed before the interleaved remainder, arm B is systematically earlier in wall-clock time than arm A for exactly the 5 tasks used in the positive control and the memorization calibration bar — a temporal confound (model/infra drift, caching, load) that lands on the one subset of tasks the run leans on hardest for validity. If instead the two rules are reconciled some other way at execution time, that reconciliation is being decided after registration, which is exactly the undisclosed analytic/execution flexibility this format is supposed to foreclose. Either reading is a problem.

*Fix.* Pick one and state it explicitly. Cleanest options: (a) drop C6 from the 300 and make it a strictly additional 25-call pilot run before the shuffle, logged and reported separately from the main 300; or (b) explicitly redefine the call order as 'C6's 25 calls first, in their own fixed order, then the remaining 275 shuffled' and carry that asymmetry into the analysis (e.g. flag the 5 C6 tasks and check the primary result is not driven by them).

**2. Stale/incorrect cross-reference between the specified/unspecified split and control C1**

*Problem.* The Reference fingerprint paragraph states: 'This split is used in the secondary analysis below and replaces hand-written reference implementations in control C1.' But C1 as defined in this same document is 'run each task's canonical solution against its 20 probes twice; fingerprints identical' — a pure determinism check with no hand-written implementations anywhere in it. The description of 'hand-written implementations' matches C2 ('hand-write two correct implementations that differ on exactly one edge case'), not C1.

*Why it matters.* A frozen registration's entire value is that every rule can be checked against every other rule before spend. A cross-reference that points at the wrong control is a small thing on its face, but it is direct evidence that the four-arm-to-two-arm reduction (which this document says was done 'to remove all three problems' the reviewers found) was not checked end-to-end after editing. A reader cannot currently tell what the specified/unspecified split is actually meant to replace, or whether some other frozen rule elsewhere in the document has the same kind of leftover reference from the prior version.

*Fix.* Correct the reference (almost certainly should read C2, or should describe what was cut from the four-arm design directly rather than by control number), and do one full pass matching every named control/section cross-reference in this document against its actual definition before it is re-frozen.

**3. Specified/unspecified slot split — the instrument for the central mechanistic claim is confounded with one author's coding style**

*Problem.* 'Slots where the reference returns cleanly are specified slots; slots where it raises or times out are unspecified slots.' This label is used in secondary analysis 1 to decide whether an observed effect is 'an ambiguity story' (lives in unspecified slots) or 'a correctness story' (lives in specified slots) — described as the central interpretive fork for the whole run. But the label is generated from a single canonical implementation's incidental choice to raise or not raise on an out-of-domain input, not from the actual specification. A canonical solution that happens to add a defensive `if x < 0: raise ValueError` on an input the spec never mentions gets that slot classified 'specified'; one that lets the same input crash with an uncaught IndexError gets it classified 'unspecified' — with no requirement that either choice reflects what the docstring/spec actually commits to.

*Why it matters.* This is exactly the kind of instrument-validity gap the review brief flags: a source of measured divergence (ambiguity vs. correctness) that tracks something other than the construct it claims to measure (one author's defensiveness habits, not specification completeness). Even if the primary SUPPORTED/FALSIFIED/INCONCLUSIVE call comes out clean, the headline mechanistic story the secondary analysis is built to tell ('does it live in unspecified behavior or correctness') is not well supported by this operationalization as written.

*Fix.* Either (a) validate the specified/unspecified split against an independent signal — e.g. do multiple human-written 'correct' implementations (as already done for C2's 5 tasks) actually agree on which inputs are in-spec vs. out-of-spec, before trusting the canonical solution's behavior as the arbiter — or (b) relabel the secondary analysis explicitly as 'divergence on inputs the canonical solution treats as valid vs. invalid' rather than 'specified vs. unspecified,' so the claim matches what is actually measured.

**4. Extraction-failure sentinel can inflate the primary statistic without tripping the disclosed safeguard**

*Problem.* Extraction failures get a uniform 'fingerprint of 20 ExtractionFailure slots,' so two failures agree perfectly with each other and disagree on all 20 slots with any executed rep. If one arm has a higher extraction-failure rate than the other for reasons unrelated to genuine behavioral consistency (e.g. the appended sentence changes how often the model wraps output in exactly one code fence), that arm's disagreement score is mechanically inflated by formatting noise, not measured behavioral divergence. The pre-registered safeguard (secondary analysis 2: recompute Δ excluding extraction failures) only surfaces this 'if the two disagree in sign or in SUPPORTED/FALSIFIED classification' — it says nothing about a case where extraction noise pushes an already-trending result over the line without flipping the categorical label.

*Why it matters.* The primary decision (SUPPORTED/FALSIFIED/INCONCLUSIVE) is the number this whole run is funded to produce, and it is computed on the version that includes extraction failures. A SUPPORTED call that is partly or mostly an extraction-format artifact would pass through the disclosed check silently as long as the classification label itself doesn't flip, and the consuming decision (spinning up two follow-up registrations) would then be acting on a result that isn't actually about run-to-run behavioral consistency in working code.

*Fix.* Report the magnitude of the with/without-extraction-failure difference (not just whether the categorical label flips) alongside the primary result, and set a pre-specified magnitude threshold (e.g., report INCONCLUSIVE-DUE-TO-EXTRACTION-NOISE if excluding failures moves the point estimate by more than some fraction of δ) rather than relying solely on a binary flip check.

**5. Probe randomization keyed on `hash(task name)` is not guaranteed stable across process restarts**

*Problem.* 'Slots 7–20, random in-domain probes, generated with random.Random(hash of task name)'. CPython's built-in `hash()` on strings is randomized per interpreter process by default (PYTHONHASHSEED), so the same task name produces a different seed — and therefore a different set of 'frozen' probes — in a different process invocation, unless the seed is pinned. The document itself anticipates a multi-step, possibly-interrupted run (standby task substitution, 'extend k as needed'), which is exactly the situation where a restart is plausible.

*Why it matters.* The registration's whole premise is that the 20 probes per task are 'frozen before any model call and never shown to the model.' If the harness is restarted mid-run, this rule silently produces a different probe set for the same task than whatever was used earlier in the same nominal run, breaking comparability within the dataset and making the registration's own probe set irreproducible on replication or audit — even though every other frozen rule in the document is written as if the probes are a fixed, checkable artifact.

*Fix.* Seed with something process-invariant, e.g. `random.Random(zlib.crc32(task_name.encode()))` or `hashlib.sha256(task_name.encode())`, or explicitly pin `PYTHONHASHSEED` for the entire run and record its value in the run log.

**6. Post-INCONCLUSIVE diagnosis routes on undefined terms ('near 0', 'near 1', 'mid-range')**

*Problem.* The Diagnosis section says: 'If both arms sit near 0 across most tasks, run the memorization diagnostic ... If both arms sit near 1 → temperature-1 sampling noise dominates ... Only a mid-range mean Δ whose interval straddles δ justifies a new record.' None of 'near 0', 'near 1', or 'mid-range' is given a numeric boundary anywhere in the document.

*Why it matters.* Every other decision boundary in this registration is a specific number (δ=0.05, 90% interval, p<0.05, C6's 0.02). This one governs whether the run gets diagnosed as memorization, floor effect, ceiling, or scale-up-worthy — a decision with real downstream spend consequences — and it is the one place left open to post-hoc judgment after the data are in, for exactly the reason INCONCLUSIVE outcomes are expected to be common (30 tasks, doc's own words: 'INCONCLUSIVE is the expected modal outcome').

*Fix.* Give numeric bands before the run, e.g. 'near 0' = mean disagreement(A) and (B) both < 0.05 (matching the C6 sensitivity floor of 0.02 plus a margin), 'near 1' = both > 0.8, 'mid-range' = everything else with the CI straddling δ.

### Minor findings

- **No formal power/precision justification for n=30, δ=0.05.** The document acknowledges 'at 30 tasks INCONCLUSIVE is the expected modal outcome' and accepts this as a pilot, which is a reasonable posture, but no calculation (e.g., expected CI half-width given a plausible variance of per-task disagreement) is shown to justify that 30 tasks and δ=0.05 are the right pairing rather than, say, 30 tasks being underpowered even for genuinely present effects near δ.
- **'k' used for two different quantities.** 'k = 5 completions per (task, arm)' is defined in Design. Later, the task-bank fallback text says 'extend k as needed; standbys taken in order' referring to the number of standby task names, not completions per arm. Reusing the symbol invites an implementation slip.
- **C6's threshold gloss doesn't obviously match the disagreement definition.** 'must exceed 0.02 (at least one disagreeing slot in fifty pair-slots)' — but 'Disagreement per (task, arm)' is defined as a mean of per-rep-pair fractions over 20 slots, aggregated per task, not as a pooled slot-count over 50 pair-units. It's unclear whether C6's gate statistic is meant to be the mean of the 5 per-task disagreement values or a pooled count across all 5 tasks x 10 pairs x 20 slots; these are not the same statistic in general and the parenthetical arithmetic gloss doesn't resolve which is intended.
- **'FALSIFIED' label covers a real, detectable, but small effect.** A 90% CI entirely above 0 but with point estimate below δ (e.g. [0.001, 0.04]) is classified FALSIFIED under the stated rule, even though it is evidence of a genuine nonzero effect that's just below the smallest-effect-of-interest. This is a defensible equivalence-testing choice, but the label 'FALSIFIED' may be read by later consumers as 'no effect exists,' which is a stronger claim than what was actually shown. Consider a label like 'FALSIFIED (below MSOI)' or a fourth bucket.
- **Standby task list is algorithmic, not printed.** The exact standby names beyond the 30 registered tasks aren't listed in the document; they depend on re-deriving `random.Random(20260926).sample(names, k>30)` against the same 'names' input order from the hosted Orchid-HEval file. If that hosted file's row order changes between registration and execution, the standby list silently changes. Low risk, but worth a one-line mitigation (e.g. pin a local snapshot of the 164-task list at registration time).

### Done well

- Correct unit of analysis throughout: task-paired contrast (Δ per task), task-level bootstrap, and a within-task permutation test that shuffles arm labels among each task's own completions — the right resampling scheme for a matched-pairs design.
- The fuzz instrument is genuinely frozen and validated: 20 probes per task combining deterministic edge cases with a random pool, plus control C2, which hand-writes implementations differing on exactly one edge case and requires the probes to actually separate them — a real positive control on the instrument, not just an assumption that it works.
- Execution-based correctness oracle only ('No LLM judge anywhere on the measurement path'), consistent with the project's house convention against LLM-as-judge on the measurement path.
- Explicit, narrow scope section stating what the run can and cannot claim, including naming the paraphrase-control confound as a known, disclosed limitation deferred to a specific named follow-up rather than papered over.
- Pre-spend sanity gate (C6) that can stop the run before most of the budget is spent if the instrument shows no sensitivity at all, and a determinism check (C1) and rename-integrity check (C5) that catch classes of harness bugs before they contaminate 300 model calls.
- Transparent revision history: the interval was widened from 80% to 90% in response to review, with the reasoning stated in the document rather than silently changed.
