# Independent reviews — Orchid-HEval "simple" ablation pre-registration

**Reviews:** `simple-ablation-orchid-preregistration.md`, artifact `4f67aa29-681c-420d-a68e-2441d58ed819`, version `f6685cb7-e5df-40eb-9c65-4169edf5b358`.
**Method:** two reviewers, each a fresh context that saw only the registration and the house conventions (frozen record, no LLM judge, consuming decisions required). Neither saw the other's review, the earlier task01 review log, or the same-author review (`orchid-preregistration-review-log.md`, artifact `7c464946-d0ff-46f9-aac8-aeaf6a54bc79`). Both declared full coverage (deviations: none).
**Status:** findings only — not applied. Registration stays frozen.

## Reviewer A (frame `0a0dc388-4c05-4899-b45f-7e48410f57db`)

**Verdict.** Not fundable as written. The registration has real strengths (frozen seeded task sample, execution-only oracle, controls run before spend, a bootstrap unit that now matches the true independent replicate, and an honest memorization-floor branch), but the primary inferential test does not answer the stated research question. The interval test that decides SUPPORTED/FALSIFIED is registered on disagreement(A) - disagreement(C) -- vague-'simple' vs. an operationalized-constraints arm -- not on disagreement(A) - disagreement(B), which is the actual vague-vs-nothing contrast the hypothesis is about. Because arm C's constraints mechanically shrink the space of valid implementations on a dimension (architectural restriction) that is not the dimension the fuzzer probes (behavioral divergence on edge-case inputs), a positive A>C gap is expected even under a world where 'simple' has zero effect relative to no instruction at all. Combined with an asymmetric decision rule (SUPPORTED needs only a point-estimate ordering plus one CI; FALSIFIED needs a full reversal that C's own mechanics make close to unreachable) and no pre-specified smallest-effect-of-interest, the design is structurally biased toward SUPPORTED or INCONCLUSIVE and can all but never return FALSIFIED. An undefined equality rule for the disagreement fingerprint (float tolerance, exception-matching granularity) adds a second, independent source of undisclosed analytic flexibility on the primary metric itself. These are fixable before the first model call is spent, but as registered the primary claim would not be defensible against the stated research question.

### Main findings

**1. Primary interval is on the wrong contrast: A-C is tested, A-B (the actual hypothesis) is not**

*Problem.* The stated question is whether adding 'Keep it simple.' (arm A) causes more run-to-run behavioral divergence than issuing no such instruction at all (arm B, 'absent... Baseline'). But P1's only interval test is 'the task-level bootstrap CI ... on disagreement(A) - disagreement(C) excludes 0' -- the ordering condition 'disagreement(A) >= disagreement(B)' that would actually test the A-vs-B contrast carries no CI, no permutation test, and no threshold at all; it is a bare point comparison. Arm C ('operationalized... base prompt + "Constraints: standard library only, at most one helper function, no CLI or __main__ block."') is a structural, architecture-restricting manipulation, not a de-ambiguated version of 'simple' on the dimension the fuzzer reads (behavior on 20 fuzzed inputs). A constraint like 'at most one helper function' can shrink implementation diversity, and therefore shrink measured disagreement, for reasons that have nothing to do with whether 'simple' is ambiguous -- it just narrows the space of valid programs. A statistically significant A-C gap is therefore compatible with 'simple' having no causal effect relative to doing nothing (B), so long as constraining the solution space mechanically reduces disagreement on its own.

*Why it matters.* This is the study's one confirmatory test, and it can return SUPPORTED for a reason unrelated to the causal claim in the Question section. A reviewer cannot sign off on a pre-registration whose registered statistic doesn't correspond to its registered hypothesis -- this is exactly the kind of mismatch pre-registration is supposed to prevent, and it can no longer be fixed post-hoc without unfreezing the record.

*Fix.* Make disagreement(A) - disagreement(B) the primary interval-tested contrast (same bootstrap/permutation machinery already specified for A-C), with SUPPORTED keyed to that CI excluding zero in the ambiguity-increasing direction. Keep A-C and the current A>=B>C ordering as a secondary, corroborating pattern -- useful context for how big the 'simple' effect is relative to an operationalized fix -- but not the thing that decides SUPPORTED/FALSIFIED.

**2. Asymmetric, near-unfalsifiable decision rule; no smallest-effect-of-interest**

*Problem.* SUPPORTED requires only a rank ordering (A>=B>C, unadorned by any interval) plus one CI-excludes-zero test on A-C. FALSIFIED requires the mirror-image full reversal 'if the reverse ordering holds with the equivalent CI excluding 0' -- i.e. C>=B>A with the A-C CI excluding zero in the other direction. Given Main Finding 1 (C's constraints mechanically compress the solution space), an observed C>=B>A reversal is a much rarer event than a merely-null A~B~C world, so the registration has built in a decision rule that a true null collapses to INCONCLUSIVE rather than FALSIFIED. There is also no smallest-effect-of-interest (SESOI): 'excludes 0' with 600 completions across 30 tasks can certify SUPPORTED on an effect too small to matter for the downstream consuming decision (triggering a paraphrase-controlled follow-up study).

*Why it matters.* A pre-registration that can be confirmed by a trivial effect but essentially never disconfirmed by a genuine null is not falsifiable in the sense the pre-registration format is meant to guarantee. Combined with Main Finding 1, this doubles the risk that a run returns SUPPORTED regardless of whether 'simple' itself does anything.

*Fix.* Register a smallest effect of interest delta (e.g. delta = 0.05 disagreement, picked from the fuzzer's own scale, or normalized against P3's D-arm effect size) and define FALSIFIED as 'the A-B (per Main Finding 1) CI lies entirely inside +-delta', SUPPORTED as 'the CI excludes 0 by at least delta in the ambiguity-increasing direction', and everything between as INCONCLUSIVE. This makes a plain null result (not just a reversal) a legitimate falsifying outcome.

**3. Disagreement fingerprint has no equality/tolerance rule -- undisclosed analytic flexibility on the primary metric**

*Problem.* The fuzzer explicitly generates float-typed and List[float]-typed inputs ('float -> random float', 'List[int]/List[float] -> random-length list ... of random numbers'), and 'Each run's 20-slot output/exception vector is its fingerprint,' with disagreement defined as 'mean pairwise fraction of differing slots.' Nowhere is it specified whether two float outputs are compared by exact equality, some numeric tolerance, or rounding; nor whether two exceptions are 'the same slot' when they share a type but differ in message, or differ in type but both signal an error. These are exactly the kind of small comparator choices that get made ad hoc once real completions are in hand, and they can move the disagreement statistic materially: exact float equality alone will register two functionally-identical implementations that differ only in floating-point rounding as 'disagreement,' inflating the metric for reasons unconnected to the ambiguity hypothesis, and the direction/size of that inflation is not guaranteed to be equal across arms.

*Why it matters.* This is a second, independent channel (alongside Main Finding 1) by which the primary measurement can be decided after the data is seen rather than by the frozen protocol -- the core failure mode pre-registration exists to close off.

*Fix.* Freeze the comparator now: e.g. floats compared with a fixed relative/absolute tolerance (state the exact value), exceptions compared by type only (or by type + a documented normalized message), and a worked example of two slot outputs that count as equal vs. different, committed to the record before any model call.

**4. 80% bootstrap/permutation interval is an unusually loose bar for the study's sole confirmatory claim**

*Problem.* The interval underlying both SUPPORTED and FALSIFIED is 'the task-level bootstrap CI (2000 resamples, 80% interval -- still pilot-sized at 30 tasks)'. An 80% interval is a substantially looser threshold than the 90/95% conventionally used to guard a go/no-go claim, and the registration offers no justification for the choice beyond noting the sample is pilot-sized -- which is an argument for treating the result as preliminary, not for loosening the interval that labels it SUPPORTED.

*Why it matters.* SUPPORTED is not a low-stakes label here -- it triggers a specific downstream commitment ('write a paraphrase-controlled confirmation ... before treating the word itself ... as the cause'). A looser interval raises the chance that this commitment is triggered by noise at n=30 tasks, and the permutation test does not fix this since it inherits the same threshold logic unless registered otherwise.

*Fix.* Either widen to a 90% (or 95%) interval and accept that INCONCLUSIVE will be the modal outcome at this sample size (which the floor/ceiling rule already knows how to handle), or keep 80% but explicitly label SUPPORTED at this stage as 'provisional -- warrants the paraphrase-controlled follow-up' rather than as a stopping point, so the interval's looseness is reflected in what the label is allowed to justify.

**5. Correctness-parity threshold (P2) is arbitrary, untested, and could mask a safety-relevant cost of 'simple'**

*Problem.* 'Parity holds if no arm's mean [pass rate] differs from another's by more than 1/5' -- a 20-percentage-point band with no stated justification (no power analysis, no reference to a meaningful-difference threshold) and no interval or test attached; it is a bare point-estimate comparison against a fixed cutoff.

*Why it matters.* If 'Keep it simple' measurably lowers the correctness rate (a plausible and important finding in its own right, since it would mean the ambiguity has a real behavioral cost, not just a 'silent decision' cost), a swing of up to 19 points would still be reported as 'parity holds,' and the registration gives P2 no path to a properly quantified effect size or interval the way P1 gets one.

*Fix.* Either derive the 1/5 band from a stated minimal-importance threshold (and add a CI on the pairwise pass-rate differences, analogous to P1's bootstrap), or drop the fixed-threshold framing and just report the pass-rate differences with their task-level bootstrap CIs as a descriptive secondary result.

### Minor findings

- **P3 ratio (disagreement(A)/disagreement(D)) is unstable near a small denominator.** If disagreement(D) (the calibration/Vagueness_prompt arm) comes out near zero for some tasks, the per-task or aggregate ratio blows up or is undefined. No smoothing, floor, or reporting convention (e.g. report the ratio only when disagreement(D) exceeds some minimum, or report the two quantities separately with a difference instead of a ratio) is specified for that case.
- **No power/sample-size justification for k=5 reps x 30 tasks.** The registration is candid that the CI is 'still pilot-sized,' but there is no a priori power calculation tying 30 tasks / 5 reps to a specific detectable effect size, which makes it hard to know in advance whether INCONCLUSIVE is the likely outcome regardless of a true effect's presence.
- **C2 positive-control pass bar (4/5 tasks) has no stated action for a 3/5 or worse result short of a full stop.** 'Any C1-C5 failure stops the run' implies <4/5 counts as failure, but this is left implicit rather than stated as the explicit pass/fail line for C2.
- **Per-task disagreement estimate rests on only 5 reps (10 pairs).** Aggregating across 30 tasks is the right level for the primary CI, but the within-task disagreement values feeding that aggregate are themselves fairly noisy with only C(5,2)=10 pairwise comparisons per task/arm; worth reporting the within-task variance alongside the between-task bootstrap so a reader can see how much of the CI width comes from which level.
- **Renamed-entry-point mitigation may not fully suppress memorization from docstring content.** Stripping the function name is a good, uniform (non-confounding) mitigation, but some HumanEval docstrings contain example I/O pairs or phrasing distinctive enough to cue retrieval independent of the name; the existing similarity-based diagnostic and INCONCLUSIVE-DUE-TO-MEMORIZATION fallback should catch this, but it's worth noting the mitigation is partial by construction.

### Done well

- Task sample is drawn with a fully reproducible, seeded procedure (random.Random(20260926).sample) and a pre-specified fallback rule for dropped tasks, rather than being chosen after looking at the tasks.
- Correctness is scored by an execution-based oracle only ('pass/fail only. No LLM judge anywhere on this path'), consistent with the project's ban on LLM-as-judge on the measurement path.
- The 20 fuzzed probe inputs per task are generated and frozen 'before any model call and never shown to the model,' closing off a leakage/optimization path that the fuzzer itself could otherwise open.
- Malformed or unparseable completions are folded into the metric as maximally divergent rather than dropped, which avoids survivorship bias in the disagreement statistic.
- The bootstrap now correctly resamples at the task level (the true independent unit) rather than at the rep or run-pair level, fixing the pseudo-replication problem that would otherwise inflate apparent precision.
- A concrete, pre-specified memorization diagnostic (SequenceMatcher similarity to the canonical solution) plus a distinct INCONCLUSIVE-DUE-TO-MEMORIZATION outcome label shows real engagement with a benchmark-specific internal-validity threat, and the renaming mitigation is applied identically across all arms so it does not itself introduce a confound.
- Controls (C1-C5) are scheduled to run before any of the 600 paid model calls, each with a concrete pass/fail criterion, and an explicit stop rule if any control fails.
- The Scope section states plainly what the run can and cannot support (single word, single-shot, function-level only), pre-empting overgeneralization of a positive result.

## Reviewer B (frame `3a63e1b0-c839-47e4-83a9-9db6e7852693`)

**Verdict.** Not fundable as written. The registration has a genuinely good skeleton — task-level bootstrap/permutation inference (correctly fixing the pseudo-replication problem it names), pre-specified controls run before any model spend, a real memorization mitigation and diagnostic, and an honest Scope section — but the primary test (P1) does not cleanly test the stated causal claim. The 'operationalized' arm (C) manipulates code-structure specificity, not the behavioral ambiguity the fuzzing instrument reads, so a low disagreement(C) is not unambiguous evidence that resolving 'simple' reduces interpretive divergence. The SUPPORTED/FALSIFIED decision rule is asymmetric: a genuine null (no effect of 'keep it simple') cannot register as FALSIFIED, only as INCONCLUSIVE, which then triggers diagnostic/redesign branches rather than acceptance of the null — while only a reversed effect can falsify. And the fuzz-input generation/comparison rules that are described as 'frozen before any model call' actually leave the numeric ranges, string/list length distributions, and slot-equality tolerance (especially for floats) unspecified, which is exactly the kind of analytic flexibility a pre-registration is supposed to close off. These are fixable with concrete edits (below), not a fundamental redesign, but they should be resolved and the document re-frozen before any of the 600 model calls are spent.

### Main findings

**1. Arm C ('operationalized') manipulates a different dimension than the fuzzer reads**

*Problem.* Arm C's text is "Constraints: standard library only, at most one helper function, no CLI or __main__ block" — a code-structure/style constraint. The disagreement instrument is entirely behavioral: it fingerprints each completion by its outputs/exceptions on 20 fuzzed inputs. Nothing in C's constraint set addresses how the function should behave on edge cases (empty input, negative numbers, boundary values, error vs. return-value semantics) — the actual locus of the interpretive ambiguity that arm A ('Keep it simple') is hypothesized to leave open. C is a plausible operationalization of 'simple as code style' but not of 'simple as behavior', while the fuzzer only ever sees behavior.

*Why it matters.* P1's SUPPORTED criterion hinges on disagreement(A) − disagreement(C) having a CI that excludes 0. If C happens to show lower disagreement, that is equally consistent with 'explicit constraints of any kind narrow the model's implementation search space and incidentally reduce behavioral variance' as with 'operationalizing simple resolves the ambiguity simple leaves open.' The registration cannot distinguish these two explanations from the data it collects, yet P1's consuming decision (write a paraphrase-controlled follow-up treating the word itself as the cause) treats the result as evidence about the word 'simple' specifically.

*Fix.* Redefine arm C so it operationalizes the same axis the fuzzer measures: e.g. append an explicit behavioral contract drawn from the task's own docstring (edge-case handling, return-vs-raise convention) rather than a code-style constraint list. Alternatively, add a fifth arm that holds prompt length/specificity constant with A while removing the word 'simple' (a length-and-specificity-matched control), so the A-vs-C gap can be partitioned into 'effect of any added constraint' vs 'effect of resolving the specific ambiguity simple introduces.'

**2. SUPPORTED does not require a statistically tested A-vs-B gap**

*Problem.* P1 requires the ordering disagreement(A) ≥ disagreement(B) > disagreement(C), but only the A−C difference gets a bootstrap CI / permutation test. The A-vs-B piece of the ordering is enforced only as a point-estimate inequality with no uncertainty quantification, and it is a weak inequality (≥), so A can be statistically indistinguishable from B (or even numerically equal) and the ordering still holds.

*Why it matters.* The research question is specifically about the word 'simple' — whether an instruction containing it causes divergence beyond having no such instruction at all (B). A result pattern where A ≈ B but C is significantly lower than both would satisfy P1's SUPPORTED criterion in full, yet it would actually be evidence that adding any explicit constraint reduces disagreement relative to an unconstrained baseline — not evidence that 'keep it simple' itself is doing anything over silence. This is the same underlying gap as finding 1, compounding it: the arm most likely to be conflated with a structural effect (C) is the only one with a statistical test attached to it.

*Fix.* Add a CI/permutation test on disagreement(A) − disagreement(B) as a co-requirement for SUPPORTED, not just a directional inequality. If A is not significantly different from B, the result should not be labeled SUPPORTED regardless of the A-C comparison.

**3. The decision rule cannot be falsified by a genuine null — only by a reversed effect**

*Problem.* FALSIFIED requires the reverse ordering (disagreement(C) > disagreement(A)) with the equivalent CI excluding 0 in that direction. A true null result — A, B, and C all show statistically indistinguishable disagreement, i.e. 'keep it simple' does nothing measurable — falls into 'otherwise', which is INCONCLUSIVE, not FALSIFIED. INCONCLUSIVE then routes into the floor/ceiling rule, which prescribes fixing the instrument, lowering temperature, running the memorization diagnostic, or scaling up tasks/reps — every INCONCLUSIVE branch is an instruction to keep investigating, not to accept the null.

*Why it matters.* This is a one-sided evidentiary structure: the hypothesis ('simple causes divergence') has a clear path to being confirmed and a path to being reversed, but no path to being cleanly rejected by 'no effect found.' Combined with the escalation logic in the floor/ceiling rule, a genuine null result is systematically re-interpreted as an instrumentation or power problem rather than as evidence against the hypothesis, which is a textbook confirmation-bias structure for a document that explicitly forbids LLM-as-judge but has not applied the same rigor to its own statistical decision rule.

*Fix.* Add an explicit FALSIFIED-by-null branch: e.g. if the A−C (and A−B) CIs both include 0 at the registered interval AND the floor/ceiling diagnostics rule out a floor/ceiling/memorization artifact, register that as FALSIFIED (or a distinct 'NULL, not artifactual' label with its own consuming decision), not INCONCLUSIVE. The current INCONCLUSIVE bucket should be reserved for cases where a diagnosed instrument problem (floor, ceiling, memorization) is actually present, not for a clean null.

**4. Disagreement metric conflates behavioral-interpretation divergence with code-robustness failures**

*Problem.* The extraction rule folds 'no fenced code block found' and SyntaxError/ImportError failures into the fingerprint as 'all-slots-error,' scored as 'maximally divergent from every other outcome.' It is not specified whether two reps that both fail (e.g. two SyntaxErrors) are scored as agreeing (same fingerprint) or as maximally disagreeing with each other. If the latter, the metric actively penalizes consistent failure as if it were behavioral disagreement.

*Why it matters.* If arm A ('keep it simple') increases the model's raw rate of producing broken/unparseable code — a well-documented side effect of terse-code instructions, unrelated to making different-but-valid interpretive choices about unspecified behavior — that alone could drive the entire A-vs-C disagreement gap through a mechanism that has nothing to do with the hypothesized 'silent incompatible decisions.' The design has no way to separate these two mechanisms in the reported aggregate, so a positive P1 result would be uninterpretable between 'simple causes divergent interpretations' and 'simple causes more broken code.'

*Fix.* Report and preserve a separate per-arm 'catastrophic failure rate' (fraction of reps hitting no-fenced-block/SyntaxError/ImportError) alongside the disagreement metric, and define explicitly whether two co-failed reps count as matching or as maximally diverging. Consider excluding catastrophic failures from the pairwise disagreement calculation (tracking them only via the separate failure-rate statistic) so disagreement measures behavioral divergence among code that actually ran.

**5. Fuzz-input generation and slot-equality rules are not actually frozen**

*Problem.* The typing rule leaves several generative parameters undefined: 'task-appropriate range' for int/float generation (no bound given), the length distribution for random ASCII strings ('varying length including empty'), and the length/magnitude distribution for random lists. Separately, the document never states what counts as two slots 'differing' — exact equality is unambiguous for ints/strings/bools, but is undefined for float and List[float] outputs, where floating-point representation or legitimate precision differences could register as spurious disagreement unrelated to any interpretive choice.

*Why it matters.* The document repeatedly emphasizes that the fuzz inputs are 'frozen per task before any model call' and that the typing rule is fixed — but the actual numeric ranges and equality tolerance are exactly the parameters that determine whether the instrument is sensitive to real behavioral divergence versus noise, and they are left to be decided when the fuzzer 'is actually coded' (per C5's own caveat). That is analytic flexibility smuggled into what is presented as a frozen instrument, and it can be tuned (consciously or not) after early results are seen.

*Fix.* Pin exact ranges/distributions now (e.g., ints/floats uniform in [-1000, 1000]; ASCII strings length ~ Uniform(0,50); lists length ~ Uniform(0,10) of the same numeric range) and pin a float-comparison tolerance (e.g., relative tolerance 1e-6, or exact-match with documented rounding) before generating the 20 probes per task.

**6. 80% confidence interval on a 30-task pilot with no power analysis, gating a real downstream decision**

*Problem.* P1's SUPPORTED/FALSIFIED test is gated on an 80% bootstrap CI (2000 resamples) over only 30 tasks, explicitly self-described as 'still pilot-sized.' No power calculation is given showing this combination can reliably detect an effect size the team would consider meaningful, nor a justification for 80% rather than a conventional 90/95% level.

*Why it matters.* The consuming decision for SUPPORTED is to invest in a further paraphrase-controlled study; for FALSIFIED it is to drop the hypothesis for this task family. Both are real resource commitments riding on a threshold that, at n=30 and 80% coverage, has a non-trivial chance of excluding 0 by chance alone even under a true null — the interval choice trades Type I error for narrower intervals at exactly the decision point where false positives are costliest (triggering unnecessary follow-up work).

*Fix.* Either raise the interval to 90/95% and accept that INCONCLUSIVE will be more common at n=30, or run a pre-registered power/sensitivity analysis (e.g. via the permutation null already specified) showing what minimum detectable effect the 30-task/5-rep design actually supports at the chosen coverage level, and report that number in the document.

**7. P2 correctness-parity threshold (0.2 absolute) is loose and unjustified**

*Problem.* Parity holds if no arm's mean pass rate differs from another's by more than 1/5 (an absolute 20-percentage-point band). No justification is given for this figure, and it is large relative to typical pass@1 spreads on HumanEval-style tasks.

*Why it matters.* A real accuracy cost of the 'operationalized' constraint (arm C) — plausible, since banning helper functions and CLI/__main__ blocks could force worse solutions on some tasks — could be as large as 19 points and still be waved through as 'parity,' masking a tradeoff that would materially change how the P1 result should be read (a low-disagreement arm that is also a lower-correctness arm is not simply 'ambiguity resolved for free').

*Fix.* Tighten the band (e.g. to a value derived from the expected binomial noise at 30 tasks × 5 reps, such as 2 SEs of the pooled pass-rate difference) or report the raw per-arm pass rates with their own CIs regardless of the pass/fail threshold, so a real tradeoff is visible in the write-up even if it doesn't cross the parity-failure line.

### Minor findings

- **Model identity not pinned in the document.** The model is `host.reasoning_model()`, resolved at run time and logged after the fact rather than named in the registration. Acceptable given the mid-run-change invalidation rule, but means the registration itself does not commit to a specific, checkable model identity in advance.
- **Temperature value not stated.** 'Temperature: fixed default, also snapshotted into the run log' — the actual numeric value (or 'no temperature parameter passed') should be stated now rather than deferred entirely to the log, since 'default' could mean different things depending on how the call is constructed.
- **C2 and memorization thresholds are unjustified round numbers.** The positive-control bar ('at least 4 of the 5 tasks') and the memorization cutoff ('≥0.85 similarity on ≥20 of 30 tasks') are reasonable-looking but presented without any rationale (e.g., simulation, prior benchmark data) for why those specific numbers were chosen over adjacent ones.
- **C5's '100% coverage' claim is structural, not executed, at registration time.** The document itself flags that the type-coverage check needs re-verification 'once the fuzzer is actually coded.' This is honestly disclosed, but means one of the five pre-model-call gates is not actually satisfied yet at the time of freezing — worth a checklist item confirming it before the 600 calls, not just a note in the text.
- **No multiple-comparison consideration across P1 and P2.** Two separate inferential tests (P1's CI/permutation test, P2's parity check) are run on overlapping data with no discussion of joint error rates. Likely low-stakes given P2 is a threshold rule rather than a formal test, but worth a one-line acknowledgment.

### Done well

- Bootstrap and permutation inference correctly resample at the task level (the true independent unit), explicitly fixing a named pseudo-replication problem from prior work rather than resampling within-arm run-pairs or individual reps.
- All five controls (C1-C5) are scheduled to run before any of the 600 model calls, with an explicit stop rule ('Any C1-C5 failure stops the run before a single model call is spent'), which is real protection against wasting budget on a broken instrument.
- The memorization confound is both diagnosed (canonical-solution similarity check) and pre-emptively mitigated (neutral entry-point renaming applied uniformly across all arms, so it cannot become a differential confound), and the document is explicit that this closes 'an internal-validity gap found in review.'
- Arm D (Orchid's own validated ambiguity manipulation) is correctly scoped as a descriptive calibration reference (P3) rather than given a SUPPORTED/FALSIFIED label it doesn't deserve.
- Every outcome (SUPPORTED/FALSIFIED/INCONCLUSIVE) has an explicit, concrete consuming decision attached, including a sensible requirement that a SUPPORTED result be followed by a paraphrase-controlled check before attributing the effect to the word 'simple' itself rather than to prompt rephrasing in general.
- The correctness oracle is purely execution-based (test_case pass/fail), with no LLM-as-judge anywhere on the measurement path, consistent with the stated house convention.
- An explicit Scope section bounds what the run can and cannot claim (single-shot, function-level only; no generalization to other specification words without separate testing), which limits post-hoc overclaiming.
- Dropout/replacement handling (a pre-drawn standby task at seed k=31) avoids ad hoc, potentially biased replacement decisions after seeing which tasks fail to classify.
